Drop Vue onto any HTML page. No build step. No CLI. Ideal for progressively enhancing existing sites.

Vue vs React vs Angular

React

  • Library, not a full framework
  • You pick routing, state, tooling
  • JSX — JavaScript-centric
  • Huge ecosystem
  • More decisions out of the box

Vue 3 ← We're here

  • Full framework, progressive
  • Official Router + Pinia (state)
  • HTML-centric templates
  • Best beginner DX
  • Scales to enterprise with Nuxt

Angular

  • Full framework, strongly opinionated
  • TypeScript required
  • Enterprise-first design
  • Steeper initial curve
  • Great for large teams

There's no objectively wrong choice. Vue's unique strength is that it's readable from day one — the template syntax maps directly to how you already think about HTML.

Don't let the comparison paralyze you. Learn Vue. Everything you learn here transfers — reactivity, components, event handling — these are cross-framework concepts.

Two Ways to Write Components

Options API — the original


<script>
export default {
  data() {
    return { count: 0, name: 'Vue' }
  },
  computed: {
    message() {
      return `${this.name}: ${this.count}`
    }
  },
  methods: {
    increment() { this.count++ }
  },
  mounted() {
    console.log('Component mounted')
  }
}
</script>

Composition API — Vue 3 native


<script setup>
import { ref, computed, onMounted } from 'vue'

const count = ref(0)
const name  = ref('Vue')

const message = computed(() =>
  `${name.value}: ${count.value}`
)

function increment() { count.value++ }

onMounted(() => {
  console.log('Component mounted')
})
</script>

Use Composition API + <script setup> for new projects. The Options API is still fully supported — you'll encounter it in older codebases.

The Composition API is a superset of the Options API conceptually. Everything you could do in Options API, you can do in Composition — usually more cleanly.

The Real Win: Composables


// composables/useCounter.js
// Reusable logic — use in ANY component
import { ref, computed } from 'vue'

export function useCounter(initial = 0) {
  const count   = ref(initial)
  const doubled = computed(() => count.value * 2)
  const isEven  = computed(() => count.value % 2 === 0)

  function increment() { count.value++ }
  function decrement() { count.value-- }
  function reset()     { count.value = initial }

  return { count, doubled, isEven, increment, decrement, reset }
}

// composables/useFetch.js
import { ref, onMounted } from 'vue'

export function useFetch(url) {
  const data    = ref(null)
  const loading = ref(true)
  const error   = ref(null)

  onMounted(async () => {
    try {
      const res  = await fetch(url)
      data.value = await res.json()
    } catch (e) {
      error.value = e
    } finally {
      loading.value = false
    }
  })

  return { data, loading, error }
}

What is a composable?

A function that uses Vue's reactivity system to encapsulate and reuse stateful logic across components.

Why this matters

Everything you used to do with mixins — without the naming conflicts, implicit dependencies, or unclear source of data.

VueUse

200+ open-source composables for common browser tasks: useDark, useStorage, useFetch, useMediaQuery, and more.

💡 Convention

Composable function names always start with use. This is a widely followed convention across the ecosystem.

Composables are the #1 reason I recommend learning Composition API over Options API for new developers. The reusability model is far superior.

09 / 32

ref vs reactive

ref — for any value


import { ref } from 'vue'

const count   = ref(0)         // primitive
const name    = ref('Nerando') // string
const tags    = ref(['vue'])   // array
const user    = ref({ id: 1 }) // object

// script: always .value
count.value++
name.value = 'Nerajno'
tags.value.push('nuxt')

// template: auto-unwrapped
// {{ count }}  {{ name }}

reactive — for objects


import { reactive } from 'vue'

const user = reactive({
  name: 'Nerando',
  role: 'developer',
  skills: ['Vue 3', 'TypeScript']
})

// No .value — plain property access
user.name = 'Nerajno'
user.skills.push('Nuxt')

// ⚠ Destructuring breaks reactivity!
const { name } = user // ❌ no longer reactive
// Fix: use toRefs()
import { toRefs } from 'vue'
const { name } = toRefs(user) // ✅

The Vue team's recommendation: default to ref for everything. Use reactive when you have a clearly related group of state and prefer dot-notation access.

Computed Properties


<script setup>
import { ref, computed } from 'vue'

const forecasts = ref([
  { id: 1, city: 'Atlanta',     temp: 88, condition: 'sunny'  },
  { id: 2, city: 'Seattle',     temp: 52, condition: 'rainy'  },
  { id: 3, city: 'Denver',      temp: 41, condition: 'cloudy' },
])
const filter = ref('all')

// Cached — only recalculates when forecasts or filter changes
const filtered = computed(() => {
  if (filter.value === 'hot')   return forecasts.value.filter(f => f.temp >= 75)
  if (filter.value === 'cold')  return forecasts.value.filter(f => f.temp < 55)
  return forecasts.value
})

// Derived values — auto-updates cascade
const avgTemp     = computed(() => {
  const sum = forecasts.value.reduce((acc, f) => acc + f.temp, 0)
  return Math.round(sum / forecasts.value.length)
})
const hotCount    = computed(() => forecasts.value.filter(f => f.temp >= 75).length)
const coldCount   = computed(() => forecasts.value.filter(f => f.temp < 55).length)
</script>

Cached

Computed only recalculates when reactive dependencies change. Efficient for expensive transformations.

vs methods

A method would recalculate on every render. Computed is cached between dependency changes.

Rule of thumb

If it can be derived from existing state, make it computed — not a method, not another ref.

Watch & WatchEffect

watch


import { ref, watch } from 'vue'

const query = ref('')

// Lazy: runs on change
// Gets old + new value
watch(query, (newVal, oldVal) => {
  console.log(`${oldVal} → ${newVal}`)
  fetchSearch(newVal)
})

// Watch multiple sources
watch([query, filter],
  ([q, f]) => search(q, f)
)

watchEffect


import { ref, watchEffect } from 'vue'

const count = ref(0)
const label = ref('')

// Runs immediately
// Auto-tracks ALL reactive
// dependencies it touches
watchEffect(() => {
  label.value =
    `Count: ${count.value}`
  // No need to list deps
})

Cleanup


// Stop a watcher manually
const stop = watch(query, fn)
stop() // call to stop

// Clean up side effects
watchEffect((onCleanup) => {
  const timer = setTimeout(
    () => { /* do work */ }, 300
  )
  onCleanup(() => {
    clearTimeout(timer)
  })
})

Use watch when you need old vs new comparison, or want lazy execution. Use watchEffect for immediate execution and auto-tracked dependencies.

Lifecycle Hooks

onBeforeMountBefore first render. DOM not ready.
onMountedDOM is live. Most commonly used. Fetch data, init third-party libs.
onBeforeUpdateBefore reactive data causes re-render.
onUpdatedAfter a reactive change updates the DOM.
onBeforeUnmountCleanup: clear intervals, remove listeners.
onUnmountedComponent removed from DOM. Final cleanup.

<script setup>
import {
  ref,
  onMounted,
  onBeforeUnmount
} from 'vue'

const currentTime = ref('')

// Set up when component mounts
const interval = setInterval(() => {
  currentTime.value = new Date()
    .toLocaleTimeString()
}, 1000)

// Tear down when it unmounts
// Always clean up after yourself!
onBeforeUnmount(() => {
  clearInterval(interval)
})
</script>

<template>
  <p>{{ currentTime }}</p>
</template>
onMounted is the one you'll use in 80% of cases. onBeforeUnmount for cleanup. Memorize those two and look up the rest when you need them.

Single-File Components


<!-- WeatherCard.vue -->

<script setup>
import { ref } from 'vue'

const props = defineProps({
  forecast: {
    type: Object,
    required: true
  }
})

const emit = defineEmits(['save', 'remove'])
const isExpanded = ref(false)
</script>

<template>
  <article
    class="card"
    :class="{ saved: forecast.saved }"
  >
    <header @click="isExpanded = !isExpanded">
      <h3>{{ forecast.city }}</h3>
      <span>{{ isExpanded ? '▲' : '▼' }}</span>
    </header>

    <p v-if="isExpanded">
      {{ forecast.temp }}°F · {{ forecast.condition }}
    </p>

    <footer>
      <button
        @click="emit('save', forecast.id)"
        :disabled="forecast.saved"
      >{{ forecast.saved ? '✓ Saved' : 'Save' }}</button>

      <button @click="emit('remove', forecast.id)">
        Remove
      </button>
    </footer>
  </article>
</template>

<style scoped>
.card { border-radius: 10px; border: 1px solid #2a2a4a; padding: 1rem; }
.saved header { opacity: 0.5; }
</style>

3 sections. 1 file.

Logic, template, and styles co-located. Drop the file into any project and it works.

defineProps

Declare what data the parent can pass in. Vue validates at runtime in development.

defineEmits

Declare what events this component can send upward. Makes the component's API explicit and self-documenting.

Local state

isExpanded is private to this component. The parent doesn't know about it — nor should it.

Props Down · Events Up

Parent (App.vue) — sends data + listens


<script setup>
import { ref } from 'vue'
import WeatherCard from './WeatherCard.vue'

const forecasts = ref([
  { id: 1, city: 'Atlanta', temp: 88, condition: 'sunny',  saved: false },
  { id: 2, city: 'Seattle', temp: 52, condition: 'rainy',  saved: false }
])

function save(id) {
  const f = forecasts.value.find(f => f.id === id)
  if (f) f.saved = true
}

function remove(id) {
  forecasts.value = forecasts.value.filter(f => f.id !== id)
}
</script>

<template>
  <WeatherCard
    v-for="forecast in forecasts"
    :key="forecast.id"
    :forecast="forecast"
    @save="save"
    @remove="remove"
  />
</template>

Child (WeatherCard.vue) — receives + emits


<script setup>
defineProps({ forecast: Object })
const emit = defineEmits(['save', 'remove'])
</script>

<template>
  <div>
    <h3>{{ forecast.city }}</h3>
    <p>{{ forecast.temp }}°F · {{ forecast.condition }}</p>
    <button @click="emit('save', forecast.id)">
      Save
    </button>
    <button @click="emit('remove', forecast.id)">
      Remove
    </button>
  </div>
</template>

WeatherCard never modifies the forecast directly. It asks the parent to do it via events.

Props down, events up is the law. Not a guideline. Every time you want to break this pattern, there's a better solution that works with it.

Slots — Component Content Injection


<!-- BaseCard.vue — reusable shell -->
<template>
  <div class="base-card">
    <header v-if="$slots.header">
      <slot name="header" />
    </header>

    <main>
      <!-- Default slot: unnamed -->
      <slot />
    </main>

    <footer v-if="$slots.footer">
      <slot name="footer" />
    </footer>
  </div>
</template>

<!-- Parent — fills the slots -->
<BaseCard>
  <template #header>
    <h2>Profile Card</h2>
  </template>

  <!-- Default slot content -->
  <p>Nerando Johnson</p>
  <p>Frontend Developer</p>

  <template #footer>
    <button>Follow</button>
  </template>
</BaseCard>

What slots do

Let a parent inject HTML content into a child component — without the parent knowing about the child's internal structure.

Named slots

Multiple injection points in one component. Use #name shorthand in the parent: <template #header>.

Default slot

Unnamed slot — the content between the component tags goes here. Every component can have one.

Slots are how you build generic layout components that any content can be passed through.

Slots are the third data-passing mechanism after props and events. Props = data, Events = messages, Slots = markup. Each has its place.

The Complete Directives Reference

v-bind ( : )

Bind any attribute to reactive data
:href="url"   :class="{ active }"   :style="obj"

v-on ( @ )

Handle DOM events with modifiers
@click="fn"   @submit.prevent   @keyup.enter   @click.stop

v-model

Two-way binding: text, textarea, checkbox, radio, select
v-model="value"   v-model.trim   v-model.number

v-if / v-else-if / v-else

Conditional rendering — element removed from DOM when false. Use v-show for frequent toggling (CSS only).

v-for — always with :key

Loop over arrays, objects, or ranges. :key must be unique and stable — use an ID, not array index for dynamic lists.
v-for="(item, i) in items" :key="item.id"   v-for="(val, key) in obj" :key="key"

These five patterns and their shorthands (:, @) cover 95% of everything you'll write in Vue templates. The rest is niche.

Directives Combined


<script setup>
import { ref, computed } from 'vue'

const search   = ref('')
const filter   = ref('all')
const newSkill = ref('')
const skills   = ref([
  { id: 1, name: 'Vue 3', level: 'learning' },
  { id: 2, name: 'TypeScript', level: 'intermediate' },
])

const visible = computed(() =>
  skills.value
    .filter(s => filter.value === 'all' || s.level === filter.value)
    .filter(s => s.name.toLowerCase().includes(search.value.toLowerCase()))
)

function add() {
  if (newSkill.value.trim()) {
    skills.value.push({ id: Date.now(), name: newSkill.value.trim(), level: 'learning' })
    newSkill.value = ''
  }
}
</script>

<template>
  <input v-model="search" placeholder="Search skills..." />

  <select v-model="filter">
    <option value="all">All</option>
    <option value="learning">Learning</option>
    <option value="intermediate">Intermediate</option>
  </select>

  <ul v-if="visible.length > 0">
    <li
      v-for="skill in visible"
      :key="skill.id"
      :class="skill.level"
    >{{ skill.name }}</li>
  </ul>
  <p v-else>No skills match.</p>

  <input v-model="newSkill" @keyup.enter="add" placeholder="Add a skill" />
  <button @click="add">Add</button>
</template>
v-model search, v-model select, v-if, v-else, v-for, :key, :class, @keyup.enter, @click. Everything in one focused component. This is production-ready Vue.

<script setup>
import { ref, computed } from 'vue'
import WeatherSearch from './components/WeatherSearch.vue'
import WeatherCard   from './components/WeatherCard.vue'
import WeatherFilter from './components/WeatherFilter.vue'

const forecasts = ref([
  { id: 1, city: 'Atlanta', temp: 88, condition: 'sunny',  saved: false },
  { id: 2, city: 'Seattle', temp: 52, condition: 'rainy',  saved: false },
  { id: 3, city: 'Denver',  temp: 41, condition: 'cloudy', saved: true  },
])

const activeFilter = ref('all')

const filtered = computed(() => {
  if (activeFilter.value === 'hot')   return forecasts.value.filter(f => f.temp >= 75)
  if (activeFilter.value === 'cold')  return forecasts.value.filter(f => f.temp < 55)
  if (activeFilter.value === 'rainy') return forecasts.value.filter(f => f.condition === 'rainy')
  return forecasts.value
})

const savedCount = computed(() => forecasts.value.filter(f => f.saved).length)

function addForecast(city) {
  forecasts.value.push({
    id: Date.now(), city,
    temp: Math.round(40 + Math.random() * 60),
    condition: ['sunny','rainy','cloudy','windy'][Math.floor(Math.random()*4)],
    saved: false
  })
}
function saveForecast(id) {
  const f = forecasts.value.find(f => f.id === id)
  if (f) f.saved = true
}
function removeForecast(id) {
  forecasts.value = forecasts.value.filter(f => f.id !== id)
}
</script>

<template>
  <div class="app">
    <h1>Weather Dashboard <span class="count">({{ savedCount }} saved)</span></h1>
    <WeatherSearch @search="addForecast" />
    <WeatherFilter :active="activeFilter" @change="activeFilter = $event" />
    <ul>
      <WeatherCard
        v-for="forecast in filtered" :key="forecast.id" :forecast="forecast"
        @save="saveForecast" @remove="removeForecast"
      />
    </ul>
    <p v-if="filtered.length === 0">No forecasts match!</p>
  </div>
</template>

Pinia — State Management Made Simple


// stores/useWeatherStore.js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useWeatherStore = defineStore('weather', () => {
  // State — same as component refs
  const forecasts = ref([])
  const filter    = ref('all')

  // Getters — same as computed
  const filtered = computed(() => {
    if (filter.value === 'hot')   return forecasts.value.filter(f => f.temp >= 75)
    if (filter.value === 'cold')  return forecasts.value.filter(f => f.temp < 55)
    if (filter.value === 'rainy') return forecasts.value.filter(f => f.condition === 'rainy')
    return forecasts.value
  })

  const savedCount = computed(() =>
    forecasts.value.filter(f => f.saved).length
  )

  // Actions — plain functions
  function add(city) {
    forecasts.value.push({
      id: Date.now(), city,
      temp: Math.round(40 + Math.random() * 60),
      condition: 'sunny', saved: false
    })
  }

  function save(id) {
    const f = forecasts.value.find(f => f.id === id)
    if (f) f.saved = true
  }

  return { forecasts, filter, filtered, savedCount, add, save }
})

Looks familiar

Pinia stores are basically composables with a name. If you understand ref and computed, you already understand 80% of Pinia.

Using the store


// Any component
import { useWeatherStore } from '@/stores/useWeatherStore'
const store = useWeatherStore()

store.add('Miami')
console.log(store.savedCount)

Same data, accessible from any component in the app — no prop drilling, no event buses.

This is the payoff of learning Composition API first. Pinia feels like a natural extension rather than a separate thing to learn.
