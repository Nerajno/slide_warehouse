The Core Insight

Your network
is a schema.

Every person you know is a record.
Every relationship has a type.
The foreign key tells you who carries the responsibility.

This is the mental model. Once you see your network as a data model, you can design it like one. The FK is the key insight — who holds it, does the work.

belongs_to · Code

belongs_to — All 5 ORMs

# Rails
class Post < ApplicationRecord
  belongs_to :user
  # user_id on posts table
end

# Sequelize
Post.belongsTo(User, {
  foreignKey: 'userId'
});
// TypeORM
@ManyToOne(() => User)
@JoinColumn()
author: User;

// Prisma
model Post {
  author   User
  authorId Int
  @relation(fields:[authorId],
            references:[id])
}

// JPA
@ManyToOne
@JoinColumn(name="user_id")
private User author;
Same pattern, every language. The FK is on the posts/entity side. You hold it, you maintain it.

has_one · Code

has_one — All 5 ORMs

# Rails
class User < ApplicationRecord
  has_one :profile
  # profile.user_id → users.id
end

# Sequelize
User.hasOne(Profile, {
  foreignKey: 'userId'
});
// TypeORM
@OneToOne(() => Profile)
profile: Profile;

// Prisma
model User {
  profile  Profile?
}

// JPA
@OneToOne(cascade = CascadeType.ALL)
@JoinColumn
private Profile profile;
Note the ? in Prisma — optional has_one. Not every user needs a profile immediately. Same for mentees — the relationship is optional until it exists.

has_many · Code

has_many — All 5 ORMs

# Rails
class User < ApplicationRecord
  has_many :posts
  has_many :mentees,
    class_name: "Developer"
end

# Sequelize
User.hasMany(Post, {
  foreignKey: 'userId'
});
// TypeORM
@OneToMany(() => Post, p => p.author)
posts: Post[];

// Prisma
model User {
  posts  Post[]
}

// JPA
@OneToMany(mappedBy = "author")
private List<Post> posts;
Note: TypeORM requires the inverse relationship defined on Post — p => p.author. Both sides need to know about each other. Same in networking.

Association 4 of 5 — The Most Powerful

has_many :through

Leveraging Existing Networks

You reach new people through an existing relationship. The join model is the warm introduction.

has_many :through

Cold Connection vs Warm Introduction

❄️ Cold Connection

  • No context. No trust. No history.
  • Hit rate: ~2%
  • Feels transactional
  • LinkedIn request #4,289
  • No join model — just a raw record

🔥 Warm Introduction

  • Context + trust transferred + shared history
  • Hit rate: ~60%
  • Feels like a gift
  • "You two should meet"
  • Join model carries the story

The :through model is the warm introduction. It carries the data cold connections never have.

This is the core argument. The join model has FIELDS — context, trust_level, shared_interests. That's what makes a warm intro completely different.
has_many :through

The Join Model Carries the Story

# Rails — Introduction (your join model)
class Introduction < ApplicationRecord
  belongs_to :introducer, class_name: "Developer"
  belongs_to :new_contact

  # Data a cold LinkedIn request NEVER carries:
  # context:          "Met at Connect.Tech 2024, Vue.js talk"
  # trust_level:      :warm_intro
  # shared_interests: ["Vue.js", "frontend", "community"]
end

class Developer < ApplicationRecord
  has_many :introductions, foreign_key: :introducer_id
  has_many :new_contacts, through: :introductions
end

habtm has no story. :through HAS a story. Choose based on whether the introduction matters.

This is why :through beats habtm every time trust matters. Invest in the middle relationships — the ones that become join models for you.

has_many :through · Code

has_many :through — All 5 ORMs

# Rails
class Doctor < ApplicationRecord
  has_many :appointments
  has_many :patients,
    through: :appointments
end

# Sequelize
Doctor.belongsToMany(Patient, {
  through: 'Appointment'
});
// TypeORM
@ManyToMany(() => Patient)
@JoinTable() // custom entity for data
patients: Patient[];

// Prisma (explicit join model)
model Appointment {
  doctor   Doctor
  patient  Patient
  at       DateTime
  @@id([doctorId, patientId])
}

// JPA
@ManyToMany
@JoinTable(name="appointments")
List<Patient> patients;
When you need data on the join — use an explicit join entity/model. TypeORM and Prisma both support this. That's your warm introduction with fields.

habtm vs :through

One Question Decides It

Does the connection itself have a story?

Questionhabtmhas_many :through
How did they meet?❌ No record✅ context field
When was trust established?❌ Unknown✅ timestamps
Who made the introduction?❌ No attribution✅ introducer FK
Any shared experience?❌ Just overlap✅ shared_interests
Need more data later?❌ Locked out✅ just add columns

YES to any row → use has_many :through. Default to :through when trust matters.

The decision is simple. If the HOW and WHO matters — you need a join model. Community membership? habtm is fine.

Key Options

Options That Change How Relationships Behave

dependent: :destroy

What happens when you leave?

What happens to your mentees when you exit a company or community?

through: :join_model

The warm intro

The colleague who made the introduction — that IS your :through model.

counter_cache: true

Your signal metrics

Talk count, mentee count, blog count — tracked automatically as you grow.

scope: -> { active }

Quality over quantity

Only count people who are still engaged, still in your active network.

These options matter in code AND in networking. Scope your network. Maintain the active relationships. Know what happens when someone leaves.

The Big Takeaway

has_many :through
is the most
powerful pattern.

Because real career growth comes through existing relationships — not from scratch.

Warm introductions carry trust. Cold connections carry nothing.

Let this land. The :through model is the warm introduction. Invest in the middle relationships first. Then make the ask.
