Why your side projects
should scare you a little

Nerando Johnson  ·  @Nerajno  ·  developingdvlpr.com

Who is this for?

  • You've finished the courses. You build things. Things work.
  • And yet — something feels stuck.
  • You're productive, but you're not sure you're growing.
  • You keep reaching for the patterns you already know.

This talk is for you.

How this talk started

I rebuilt my portfolio.
Then I did one thing I'd never done before.

portfolio_v3  ·  Astro 5 + Supabase + Netlify

The comfortable foundation:

  • Astro 5, TailwindCSS, MDX
  • Component architecture I knew
  • Blog setup I'd done before
  • Deploy pipeline: already familiar

The stretch goal:

Never built before

A view counter with device fingerprinting and bot detection — built on Supabase edge functions. No plugin. No tutorial.

That one decision changed what the entire project taught me.

The framework

Bloom's Taxonomy

Benjamin Bloom, 1956 — a hierarchy of cognitive learning objectives

Designed for educators. More useful for developers.

01

Six levels of cognitive depth

01RememberRecall facts, syntax, definitions
02UnderstandExplain in your own words
03ApplyUse knowledge in familiar situations
04AnalyzeBreak things apart, see connections
05EvaluateJudge, compare, make tradeoffs
06CreateProduce something new

The trap

Level 3 feels productive.

You're shipping. Things work. The feedback loop is fast and positive.

That's exactly what makes it a trap.

What the upper taxonomy actually looks like

04AnalyzeDebugging an architecture you didn't write. Understanding tradeoffs.
05EvaluateChoosing between two patterns with real context. Writing code review.
06CreateComposing tools into something that didn't exist. Mentoring someone.
Note

These aren't soft skills. This is the cognitive work of senior engineering.

The real issue

Not all building
is equal.

02

Building at level 3 — Apply

Consolidation work (not growth)
  • Following a tutorial with different variable names
  • Copying a CRUD pattern into a new domain
  • Rebuilding something in a different framework
  • Adding a feature using a pattern you've done before

This is the learning equivalent of running the same route every day and wondering why your pace isn't improving.

Building at levels 4–6

Growth work
  • Implementing a feature you've never built, with a pattern you have to research
  • Making architecture decisions with no one telling you the "right" answer
  • Reviewing your own code after two weeks and knowing what you'd change
  • Composing multiple tools into something that didn't exist before

The mechanism

The stretch goal.

03

Definition

One feature you don't

Not a project you can't finish. One deliberate element that requires you to figure something out.

Build what you know — plus one thing you don't.

Why it works — the Bloom mapping

When I built the fingerprinting feature, the taxonomy kicked in automatically:

04AnalyzeWhich browser signals are stable vs volatile?
05EvaluateWhich bot detection approach fits a portfolio context?
06CreateAn edge function that synthesized all of it.

The stretch goal is a forcing function. Without it, you drift toward comfort.

The hard part

Comfort zone
is the enemy of
the upper taxonomy.

04

What growth-level work actually feels like

Not enlightenment.
Confusion with a deadline.

One night deep in the fingerprinting logic — nothing worked. Couldn't tell if it was my hashing approach, my Supabase function, or my understanding of how the signals were collected.

The reframe

That confusion is the signal.

It's not a sign you're doing it wrong. It's a sign you're doing something that requires actual thinking.

Why side projects are the right place

  • You can break things without consequences
  • You can take three approaches and throw two away
  • You can build it the "wrong" way on purpose — to understand why it's wrong
  • You have the freedom to be confused for a while
Beginner tip

If your side project feels comfortable the whole time — that's a signal, not a reward. Add a stretch goal.

Step 01

Start with a
known foundation.

01
Known foundationAstro + Tailwind + MDX — I'd done variations of all of it. That comfort is the point.

The goal isn't to have everything be new. It's to have one thing be new.

Step 02

Identify one
uncomfortable feature.

02
Before you write a line of code — write it down"What's the one thing in this project I don't know how to build?"

If you can't think of one — if every feature feels familiar — you're building at level 3. Add something that doesn't.

Step 03

Build the comfortable
part first.

03
Ship the known stuff firstI built out the entire portfolio structure before touching the view counter.

Don't skip this. Arriving at your stretch goal with a broken base is just frustrating — not educational.

Step 04

Enter the uncomfortable
part intentionally.

04
Look for concepts, not solutionsI read about fingerprinting approaches, studied what browsers expose, then wrote my own implementation. Not a copy. A synthesis.

Resist the tutorial that solves the whole thing for you. That skips the growth.

Step 05 — the one people skip

Debrief after
you ship.

05
Write it down — even brieflyAfter the view counter was live: abstract the fingerprinting logic earlier. Better logging from day one. Test the edge function locally first.

"I built a thing" → "I understand what building that thing taught me."

The bigger picture

Why this matters
beyond you.

06

What consistent upper-taxonomy work builds

  • Opinions grounded in experience, not just preference
  • The ability to articulate why an architecture decision is better or worse
  • The capacity to offer insight on someone else's code — not just critique
  • The foundation to actually mentor someone

Side projects with stretch goals are how you turn "I can code" into "I can think about code."
